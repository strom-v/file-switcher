## Баги / риски

**1. [Исправлено] В production-сборке mitmdump запускался без `-s addon.py` — подмена файлов не работала**
`src/main/proxyController.ts` (было: строки 60-71). Аргументы для `spawn` различались в dev/prod: только dev-ветка содержала `-s <addonPath>`. Prod-ветка не подключала addon вообще. `scripts/mitmdump_entry.py` — голая обёртка `from mitmproxy.tools.main import mitmdump; mitmdump()`, без встроенной регистрации `ResponseSwitcher`. `electron-builder.yml` копирует `resources/addon.py` в `Resources/addon.py` именно для передачи флагом `-s` — `resolveAddonPath()` иначе был бы мёртвым кодом. Исправлено: ветвление убрано, `-s ${this.resolveAddonPath()}` передаётся всегда.

**2. `disableSystemProxy()` удаляет файл состояния до подтверждённого отката**
`src/main/proxySystemConfig.ts:160-169`. `clearSavedStates()` вызывается прежде, чем `await restoreSavedStates(states)`. Если пользователь отменит диалог авторизации (`osascript ... with administrator privileges`) при остановке прокси — состояние уже стёрто с диска, восстановить исходные системные прокси-настройки больше нечем ни сейчас, ни при следующем запуске (`recoverStaleSystemProxy` тоже не найдёт файл). Пользователь остаётся с прокси на `127.0.0.1:<port>` без встроенного пути отката.
**Предложение:** откатывать файл состояния только после успешного `restoreSavedStates`, либо хранить его до подтверждения успеха.

**3. `enableSystemProxy` в частично удачном пути отравляет `recoverStaleSystemProxy`**
`src/main/proxySystemConfig.ts:132-157`. Файл состояния пишется (`writeSavedStates`) до `execAsAdmin`. Если `execAsAdmin` падает (отменена авторизация), запись на диске всё равно остаётся — при следующем запуске приложения `recoverStaleSystemProxy` посчитает это "зависшим" состоянием после сбоя и попытается восстановить то, что и так не менялось, лишний раз спросив пароль/Touch ID без причины.

**4. Race condition при быстром Stop сразу после Start**
`src/main/proxyController.ts`. `start()` не async и не защищён от повторного вызова между `stop()` (обнуляет `this.child`) и последующим `spawn`/`exit` события от **старого** child-процесса, чьи слушатели остаются привязаны к своему объекту `ChildProcessWithoutNullStreams`, а не к текущему состоянию контроллера. Возможен сценарий, где `applySystemProxy`/`revertSystemProxy` двух процессов накладываются друг на друга и итоговое состояние системного прокси не совпадает с тем, что показывает UI.

**5. Возможная shell-инъекция через нестандартное имя сетевого сервиса**
`src/main/proxySystemConfig.ts:48-55, 108-123`. `execAsAdmin` двойным `.replace()` экранирует кавычки для обёртки в `sudo -n sh -c "..."` / `osascript ... with administrator privileges`, а команды для каждого `service` собираются конкатенацией строк (`"${service}"`) без честного shell-quoting. Имя сетевого сервиса в System Settings пользователь может переименовать произвольно (включая `"`, `` ` ``, `$()`); при неудачном имени возможна порча команды или, в худшем случае, выполнение произвольного кода с правами root.
**Предложение:** санитизировать/отклонять сервисы с подозрительными символами, либо перейти на `execFile` с массивом аргументов вместо строкового `sh -c`.

**6. Нет валидации `port` в main-процессе перед подстановкой в shell-команды**
`src/main/ipc.ts` → `proxy:start` берёт `port: number` из renderer без проверки диапазона/типа на стороне main (полагается только на `InputNumber min={1} max={65535}` в UI). Число в итоге попадает в собираемую shell-строку (`networksetup -setwebproxy ... ${port}`) — лучше валидировать его на границе IPC.

**7. `enableSystemProxy` молча ничего не делает, если нет активных сетевых сервисов**
`src/main/proxySystemConfig.ts:132-134`. `if (services.length === 0) return` — без ошибки и без сигнала в UI. Статус прокси при этом станет `running`, пользователь решит, что системный прокси настроен, хотя по факту ни один интерфейс не тронут.

**8. Несогласованный источник правды о сертификатах: `getCertStatus` vs `listCerts`**
`src/main/certInstaller.ts:14-27, 56-96`. `getCertStatus()`/`installCert()`/`removeCertTrust()` вызывают `security ...` без явного keychain (ищут по умолчанию across search list), а `listCerts()` жёстко читает из `~/Library/Keychains/login.keychain-db`. При нестандартной конфигурации keychain (мигрировавший `login.keychain` без `-db`, изменённый search list) `SettingsPanel` может показать противоречивую картину: "доверенный" статус, но пустой список сертификатов, либо наоборот.

## Недостающая обработка ошибок / edge cases

**9. `execAsync` не даёт различить "команда не найдена" / "нет прав" / "таймаут"**
`src/main/execAsync.ts`. Просто реджектит `error` от `child_process.exec` без таймаута и без структурирования кода ошибки. Долгая/зависшая `networksetup`/`security`-команда (бывает при системных диалогах авторизации, которые никто не закрывает) заблокирует promise на неопределённое время.
**Предложение:** добавить таймаут хотя бы для non-interactive команд (`networksetup -listallnetworkservices`, `ifconfig`).

**10. `rulesStore.saveAll` не валидирует правила перед записью на диск**
`src/main/ipc.ts` → `rules:save` принимает `Rule[]` от renderer без проверки, что `urlPattern` — валидный regex (когда `isRegex: true`) или что `localFilePath` существует. Ошибка обнаружится только в Python-аддоне (`ctx.log.warn`), который логирует в stdout — эта диагностика не долетает до UI как явное предупреждение "правило X: невалидный regex". Пользователь просто увидит, что правило не срабатывает, без объяснения причины.

**11. `addon.py` не обрабатывает отсутствие ключа `enabled`/`urlPattern`/`localFilePath` защищённо**
`resources/addon.py`. `rule.get("enabled")`, но дальше `rule["urlPattern"]` и `rule["localFilePath"]` — обычный `[]`-доступ, не `.get()`. Если `rules.json` вручную отредактирован (или испорчен параллельной записью) и в объекте правила нет одного из этих ключей — вылетит `KeyError`, не пойманный нигде внутри цикла `for rule in self.rules` (в отличие от `re.error`, `OSError`), и это уронит обработку **всего** запроса.

**12. `rulesStore.read()` при повреждённом JSON молча возвращает пустой список правил, без уведомления**
`src/main/rulesStore.ts:36-46`. При ошибке парсинга просто `console.error` (не увидит пользователь GUI-приложения) и `{ rules: [] }`. Если `rules.json` повреждён (например, приложение упало во время записи), пользователь откроет приложение и увидит пустой список правил без объяснения, что случилось с их конфигурацией — тихая потеря данных без бэкапа/уведомления.

**13. `rulesStore.write()` не атомарна**
`writeFileSync(this.filePath, ...)` напрямую перезаписывает файл. Если приложение упадёт/будет убито системой посреди записи — файл может оказаться частично записан и повреждён (см. п. 12).
**Предложение:** стандартная защита — писать во временный файл и делать atomic rename.

**14. `cert:install` / `cert:remove` в `ipc.ts` не оборачивают ошибку в понятное сообщение на уровне handler**
`installCert()`/`removeCertTrust()` бросают `Error` с текстом от `security` CLI напрямую (или generic `execAsync` error) — `SettingsPanel.tsx` ловит и показывает `err.message`, что для пользователя, скорее всего, будет сырым выводом macOS `security` тула (иногда на английском независимо от локали приложения), а не локализованным объяснением.

**15. Нет обработки истечения срока действия CA-сертификата в UI как явного предупреждения**
`SettingsPanel` показывает `expiresAt` из `listCerts()`, но не подсвечивает истёкший/скоро истекающий сертификат (нет сравнения даты с `Date.now()`, нет цветового индикатора красный/жёлтый). mitmproxy CA обычно живёт около 10 лет по умолчанию, так что не горит, но раз дата уже выводится — сравнение почти бесплатное улучшение.

**16. `useVpnStatus` polling каждые 5 секунд не останавливается, пока прокси не запущен**
`src/renderer/hooks/useVpnStatus.ts`. Опрос идёт постоянно, независимо от `status.status === 'running'`. Не баг, но лишние `execAsync('ifconfig')` вызовы, когда прокси даже не активен и индикатор VPN не так важен.

## UX-пробелы

**17. Нет предупреждения/подтверждения при смене порта во время `running`**
`SettingsPanel` блокирует `InputNumber` при `running`/`starting` — хорошо, но нет явной подсказки "остановите прокси, чтобы изменить порт" рядом с задизабленным полем.

**18. Нет диагностики "почему подмена не сработала" на уровне конкретного правила**
Пользователь видит в логе `event: "passed"` для запроса, который, по его мнению, должен был совпасть с правилом, но нет способа узнать, почему (опечатка в паттерне, файл недоступен, правило выключено) — кроме как открыть детальную панель лога и вручную сверить URL с паттерном правила.

**19. Нет счётчика срабатываний правила (hit count) в `RulesTable`**
Сколько раз правило сработало с момента запуска прокси — сразу видно "мёртвые" правила, которые никогда не матчатся.

**20. Нет поиска/фильтра в `LogPanel`**
При большом трафике (до 500 записей, `MAX_LOG_ENTRIES`) единственный способ найти нужный запрос — глазами скроллить видимые 50/100/150 записей. Даже простой текстовый фильтр по URL сильно бы помог.

**21. Нет фильтра "показывать только matched" в логе**
Тумблер "только сработавшие правила" сэкономил бы много скроллинга при тестировании конкретных подмен.

**22. `OnboardingModal` не даёт способ показать его снова**
`hasSeenOnboarding`/`markOnboardingSeen` через `localStorage`, но нет кнопки "Показать инструкцию" в UI (например, в Settings) — единственный способ вернуть онбординг сейчас — вручную чистить `localStorage`.

**23. Нет уведомления, если VPN активен именно в момент нажатия Start**
`vpnActive` показывается как статичный тег в шапке, но нет проактивного предупреждения в момент запуска прокси — пользователь может не заметить маленький тег и не понять, почему трафик через VPN-туннель не логируется.

**24. Нет экспорта лога/правил**
Ни кнопки "Export logs to file" (HAR или JSON), ни экспорта/импорта набора правил (полезно для шаринга конфигурации между машинами или сохранения пресетов).

**25. Нет группировки/дублирования правил**
Создание похожего правила ("Duplicate rule") с небольшими изменениями сейчас требует заполнять форму с нуля.

## Технический долг / несогласованность

**26. Несогласованный нейминг: `filewitcher` vs `fileswitcher`/`file-switcher`**
`src/main/main.ts` — `com.filewitcher.app`; `src/main/certInstaller.ts` — `mkdtempSync(..., 'filewitcher-certs-')`; `electron-builder.yml` — `appId: com.filewitcher.app`. Продукт называется **File Switcher** / `file-switcher` везде в остальных местах (папка проекта, `productName: FileSwitcher`, `package.json` `name`). Похоже на опечатку, растиражированную по нескольким файлам.
**Важно:** смена `appId` после публикации ломает авто-обновления/идентификацию приложения в системе — исправлять до релиза, не после.

**27. Дублирование доступа к `window.api` без единого типизированного хука/клиента**
Компоненты (`RuleFormModal`, `SettingsPanel`, `App`) обращаются к `window.api.*` напрямую вперемешку с кастомными хуками (`useProxyState`, `useVpnStatus`). Не критично, но по мере роста функциональности стоит централизовать через единый слой (уже частично сделано для proxy/vpn, но не для `cert`/`dialog`/`rules`).

**28. `START_STOP_COLOR` типизирован как `Record<string, string>` вместо `Record<ProxyStatus, string>`**
`src/renderer/App.tsx`. Теряется проверка компилятором, что все статусы из `ProxyStatus` покрыты; аналогично `statusLabels: Record<string, string>`. При добавлении нового статуса в `ProxyStatus` TS не подскажет забытые места.

**29. `resolveMitmdumpPath()`/`resolveAddonPath()` полагаются на количество `..` сегментов, привязанных к текущей структуре сборки**
Комментарий явно это признаёт ("out/main/proxyController.js -> корень проекта, два уровня вверх") — хрупко к будущим изменениям структуры `electron-vite` output, но задокументировано.

## Nice-to-have (отсутствующие, но уместные функции)

**30. Breakpoints / интерактивная модификация запроса на лету**
Charles/Fiddler/Requestly дают «поставить точку останова» и отредактировать запрос/ответ перед отправкой. Для MVP, возможно, избыточно, но логичное следующее направление, если понадобится больше, чем статическая подмена файлов.

**31. Задержка/симуляция медленной сети (throttling) для конкретного правила**
Частый сценарий тестирования — искусственная задержка ответа. Добавить поле `delayMs` в `Rule` и применить `time.sleep()` в `addon.py` перед `flow.response = ...` — относительно дешёвая фича.

**32. Подмена статус-кода / кастомных заголовков ответа для правила**
Сейчас `Rule` позволяет задать только `contentType`; нет способа замокать конкретный HTTP-код (например, 500 для теста обработки ошибок) или произвольные заголовки без замены тела.

**33. Правила с приоритетом/сортировкой при пересечении паттернов**
Сейчас первое совпавшее правило в порядке массива побеждает (`for rule in self.rules: ... return`) — работает, но в UI нет визуального указания на порядок/приоритет и нет возможности явно менять порядок (drag-n-drop в таблице), хотя порядок в `rules.json` реально влияет на поведение при перекрывающихся паттернах.
